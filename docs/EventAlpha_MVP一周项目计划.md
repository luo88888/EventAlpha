# 🚀 EventAlpha MVP 一周项目计划

## 🎯 1. MVP 定位

EventAlpha MVP 目标是在一周内完成一个可运行的热点事件驱动投资研究原型，形成从信息采集、事件结构化、影响分析到事件卡片展示的最小闭环。

本版本只保留四层：

- 📡 数据采集层
- ⚙️ 事件处理层
- 🧠 推理分析层
- 🖥️ 产品服务层

MVP 不追求完整的多 Agent 协作、自动复盘、实时行情验证、用户订阅、复杂权限系统和机构级 API。首要目标是验证核心链路是否成立：系统能否自动获取热点信息，并生成可读、可解释、可查询的事件分析卡片。

## ✅ 2. 一周交付目标

一周结束时，系统应具备以下能力：

- 定时采集 RSS、公开新闻源或手动配置的信息源。
- 将原始新闻保存为结构化原始数据。
- 从新闻中抽取事件标题、事件类型、主体、时间、摘要和来源。
- 对相似事件做基础去重，避免重复生成大量卡片。
- 使用大模型生成事件重要性评分、影响行业、潜在影响资产、因果链和风险提示。
- 提供事件列表、事件详情和事件卡片 JSON 输出。
- 提供一个简单 Web 页面或 API，方便查看最近热点事件。

## 🏗️ 3. MVP 架构

```text
📡 数据采集层
  RSS / 公开新闻 API / 手动录入
        |
⚙️ 事件处理层
  原文入库 / 事件抽取 / 结构化 / 简单去重
        |
🧠 推理分析层
  重要性评分 / 影响行业与资产 / 因果链 / 风险提示
        |
🖥️ 产品服务层
  事件列表 / 事件详情 / 事件卡片 / 简单接口
```

## 📐 4. 四层功能范围

### 📡 4.1 数据采集层

🎯 目标：稳定拿到可用于分析的热点事件原始文本。

✅ MVP 范围：

- 支持配置多个 RSS 或公开新闻源。
- 支持按固定间隔采集，例如每 30 分钟或每 1 小时。
- 支持手动触发采集，便于开发和演示。
- 保存原始标题、正文摘要、链接、来源、发布时间、采集时间。

❌ 暂不做：

- 社交媒体全量采集。
- 研报解析。
- 复杂反爬。
- 多语言大规模采集。
- 实时行情接入。

🗄️ 建议数据表：

- `raw_news`

🔑 核心字段：

- `id`
- `source`
- `title`
- `summary`
- `url`
- `published_at`
- `collected_at`
- `content_hash`

### ⚙️ 4.2 事件处理层

🎯 目标：把新闻文本转成标准化事件对象。

✅ MVP 范围：

- 调用大模型或规则抽取结构化事件。
- 抽取事件类型，例如政策、战争、贸易、利率、科技、公司公告、自然灾害。
- 抽取事件主体，例如国家、公司、机构、行业。
- 生成事件摘要。
- 根据标题、链接、主体、事件类型和时间做简单去重。
- 合并重复来源，保留来源数量。

❌ 暂不做：

- 复杂事件聚类。
- 完整时间线管理。
- 多源可信度验证。
- 旧闻重发识别。
- 事件状态流转。

🗄️ 建议数据表：

- `events`
- `event_sources`

🔑 核心字段：

- `event_id`
- `event_title`
- `event_type`
- `event_subject`
- `event_time`
- `summary`
- `source_count`
- `status`
- `created_at`

### 🧠 4.3 推理分析层

🎯 目标：为每个事件生成可解释的投资研究分析结果。

✅ MVP 范围：

- 判断事件重要性，输出 1-5 分或 S/A/B/C 等级。
- 分析可能受影响的行业。
- 分析可能受影响的资产或公司，允许先用配置表或大模型生成。
- 输出正面影响、负面影响和不确定因素。
- 输出简短因果链，说明事件如何传导到市场。
- 输出风险提示，明确不构成投资建议。

❌ 暂不做：

- 历史案例检索。
- 伪相关专用 Agent。
- 实时市场验证。
- 自动复盘学习。
- 复杂资产映射知识库。

🗄️ 建议数据表：

- `event_analysis`

🔑 核心字段：

- `event_id`
- `importance_score`
- `importance_level`
- `affected_industries`
- `affected_assets`
- `causal_chain`
- `positive_factors`
- `negative_factors`
- `risk_warning`
- `model_version`
- `created_at`

### 🖥️ 4.4 产品服务层

🎯 目标：让用户可以查看系统产出的事件卡片。

✅ MVP 范围：

- 提供事件列表接口。
- 提供事件详情接口。
- 提供事件卡片 JSON。
- 提供一个简单 Web 页面展示事件列表和详情。
- 支持按事件类型、重要性、时间筛选。
- 支持手动触发一次采集与分析，便于演示。

❌ 暂不做：

- 用户系统。
- 订阅推送。
- 微信服务号。
- 机构 API 鉴权。
- 支付系统。
- 个性化关注列表。

🔌 建议接口：

- `GET /api/events`
- `GET /api/events/:id`
- `GET /api/events/:id/card`
- `POST /api/jobs/collect`
- `POST /api/jobs/analyze`

## 📅 5. 一周开发排期

### 🏗️ Day 1：项目骨架与数据模型

🎯 目标：搭好可开发、可运行、可入库的基础工程。

📋 任务：

- 初始化后端项目结构。
- 确定数据库方案，MVP 可使用 SQLite 或 PostgreSQL。
- 建立基础数据表：`raw_news`、`events`、`event_sources`、`event_analysis`。
- 实现基础配置文件，用于管理新闻源、采集频率和模型参数。
- 实现健康检查接口。

📦 交付物：

- 后端服务可启动。
- 数据库迁移可运行。
- 基础表结构完成。

### 📡 Day 2：数据采集层

🎯 目标：完成新闻源采集和原始数据入库。

📋 任务：

- 接入 3-5 个 RSS 或公开新闻源。
- 实现采集任务。
- 实现按 URL 或内容哈希去重。
- 保存原始新闻。
- 增加手动触发采集接口。

📦 交付物：

- 可通过接口触发采集。
- 原始新闻可写入 `raw_news`。
- 每条新闻包含来源、标题、摘要、链接和发布时间。

### ⚙️ Day 3：事件处理层

🎯 目标：将原始新闻转成结构化事件。

📋 任务：

- 设计事件抽取 Prompt 或抽取规则。
- 实现从 `raw_news` 到 `events` 的处理任务。
- 抽取事件标题、类型、主体、时间和摘要。
- 实现基础重复事件合并。
- 建立 `event_sources` 关联。

📦 交付物：

- 原始新闻可生成结构化事件。
- 重复新闻不会重复生成多个相同事件。
- 事件列表接口初步可用。

### 🧠 Day 4：推理分析层

🎯 目标：生成事件投资影响分析。

📋 任务：

- 设计分析 Prompt。
- 实现重要性评分。
- 实现行业和资产影响分析。
- 实现因果链生成。
- 实现风险提示生成。
- 将分析结果写入 `event_analysis`。

📦 交付物：

- 每个事件可生成一份分析结果。
- 事件卡片核心字段完整。
- 分析内容包含因果链，而不是只有结论。

### 🖥️ Day 5：产品服务层

🎯 目标：把事件卡片对外展示出来。

📋 任务：

- 实现事件列表接口。
- 实现事件详情接口。
- 实现事件卡片 JSON 接口。
- 实现简单 Web 页面，包括事件列表、事件详情和分析内容。
- 支持按时间、类型、重要性筛选。

📦 交付物：

- 用户可以在页面中查看最近事件。
- 用户可以打开事件详情查看分析卡片。
- API 可返回结构化事件卡片。

### 🔗 Day 6：联调与演示链路

🎯 目标：打通从采集到展示的完整流程。

📋 任务：

- 串联采集、抽取、分析和展示流程。
- 增加一键演示入口。
- 准备 5-10 条测试新闻样例。
- 修复字段缺失、重复生成、分析失败等问题。
- 优化事件卡片文案。

📦 交付物：

- 可以完成一次完整演示：采集新闻 -> 抽取事件 -> 生成分析 -> 展示卡片。
- 演示数据稳定可复现。

### ✅ Day 7：验收、补漏与文档

🎯 目标：让 MVP 达到可展示、可说明、可继续迭代的状态。

📋 任务：

- 完成基础测试。
- 整理 README 和启动步骤。
- 补充接口说明。
- 补充 MVP 边界说明。
- 准备演示脚本和样例事件。

📦 交付物：

- MVP 可本地启动。
- 文档可指导他人运行。
- 演示链路完整。

## 📋 6. 事件卡片字段

MVP 事件卡片建议包含：

```json
{
  "event_id": "EVT_20260624_001",
  "title": "某国宣布新的关税政策",
  "event_type": "trade_tariff",
  "summary": "事件摘要",
  "source_count": 3,
  "importance_level": "A",
  "importance_score": 4,
  "affected_industries": ["新能源", "汽车零部件"],
  "affected_assets": ["相关行业 ETF", "出口型制造企业"],
  "causal_chain": [
    "关税上升",
    "出口成本提高",
    "相关企业利润率承压",
    "市场可能重新定价"
  ],
  "positive_factors": ["国内替代供应链可能受益"],
  "negative_factors": ["出口企业成本和订单不确定性上升"],
  "risk_warning": "该分析仅用于事件研究，不构成投资建议。"
}
```

## ✔️ 7. MVP 验收标准

### 🔍 功能验收

- 系统可以采集至少 3 个新闻源。
- 系统可以保存原始新闻。
- 系统可以从新闻中抽取结构化事件。
- 系统可以对相似新闻做基础去重。
- 系统可以生成包含重要性、影响行业、影响资产、因果链和风险提示的事件卡片。
- 系统可以通过页面或接口查看事件卡片。

### 🎬 演示验收

- 从手动触发采集到页面展示事件卡片，全流程可以在 3 分钟内完成。
- 至少准备 5 条可稳定复现的样例事件。
- 每张卡片都能解释“为什么这个事件可能影响市场”。

### 🛡️ 边界验收

- 不输出明确买入、卖出、目标价或收益承诺。
- 不依赖完整用户系统。
- 不依赖实时行情。
- 不要求自动复盘闭环。

## 💡 8. 技术建议

为了保证一周内完成，建议优先选择低复杂度技术栈：

- 后端：Python FastAPI 或 Node.js NestJS/Express。
- 数据库：SQLite 起步，后续可迁移 PostgreSQL。
- 定时任务：简单 cron、APScheduler 或 node-cron。
- 数据采集：RSS parser + 少量公开 API。
- 大模型调用：统一封装为 `LLMService`，便于后续替换模型。
- 前端：Next.js、React 或简单模板页面。

✨ 推荐原则：

- 能配置的不写死。
- 能先跑通的不复杂化。
- 先保证事件卡片质量，再扩展复杂 Agent。
- 先做同步任务，必要时再引入队列。

## ⏸️ 9. 暂缓到 MVP 之后的能力

以下能力放到下一阶段，不纳入一周 MVP：

- 可信度验证层的多源官方核验。
- 市场验证层的实时行情与异动检测。
- 复盘学习层的预测账本、自动复盘和规则更新。
- 历史案例库和历史类比 Agent。
- 伪相关过滤 Agent。
- 用户订阅、推送和权限系统。
- 多 Agent 编排框架。
- 机构 API 和商业化能力。

## 🏆 10. MVP 成功标准

MVP 成功不以功能完整为标准，而以核心假设是否跑通为标准：

- 热点信息能否被持续采集。
- 新闻能否稳定转成结构化事件。
- 大模型能否生成有解释力的事件影响分析。
- 事件卡片是否足够清晰，能让用户快速理解事件和可能影响。
- 这条链路是否值得继续扩展为完整 EventAlpha 系统。
