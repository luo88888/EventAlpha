# EventAlpha 系统功能说明

> 热点事件驱动投资研究 MVP。从 RSS 采集 → 事件抽取 → 影响分析 → 前端展示的完整闭环,附用户注册登录。
> 架构图见 [系统架构图.md](./系统架构图.md)。

## 🎯 1. 系统定位

EventAlpha 是一个**自动化热点事件投研助手**:定时抓取财经新闻,用大模型把原始新闻结构化为「事件」,再做投资影响分析(重要性、影响行业、因果链、风险提示),最后通过 Web 控制台和 API 暴露给用户。

核心价值:把「人看新闻 → 人判断影响」的流程,自动化为「系统采集 → 系统抽取 → 系统分析 → 人查阅可解释的事件卡片」。

**MVP 边界**:只做四层流水线闭环 + 基础展示 + 用户登录;不做多 Agent 协作、自动复盘、实时行情验证、复杂权限体系。

## 📐 3. 整体架构

四层流水线 + API/前端服务层 + 鉴权层:

```
📡 采集层 collectors/    RSS×5 → 去重 → raw_news
        ↓
⚙️ 处理层 processors/    raw_news → LLM 抽取 → bigram 合并 → events/event_sources
        ↓
🧠 分析层 analysis/      events → 并发 LLM → event_analysis（1:1）
        ↓
🖥️ 服务层 api/v1/ + frontend/  事件列表/详情/卡片/统计 + Next.js 前端 + 用户登录
```

上层产物表是下层输入;定时任务 `scheduler.py` 每 30 分钟串行跑完整流水线;手动触发 API 亦可用。

## 📡 4. 数据采集层

**入口**:`collectors/rss_collector.py` 的 `collect_all(db) → list[CollectStats]`

**采集源**(5 个中文财经 RSS,硬编码在 `RSS_SOURCES`):36kr、华尔街见闻、财新、新浪财经、东方财富。

**处理流程**:
1. `httpx` 拉取 feed(30s 超时,跟随重定向),`feedparser` 解析。
2. 逐条计算去重键 `content_hash = SHA-256(title.strip() + "|" + url.strip())`(64 字符 hex)。
3. 双重去重:先查 `content_hash` 命中即跳过(主键),再查 `url` 命中即跳过(备用,应对同文多 URL 分发)。
4. `summary` 去 HTML 标签、截断 2000 字。
5. 写入 `raw_news`,新行 `extract_status = 'pending'`。

**产物表 `raw_news`**:source / title / summary / url / content_hash(唯一)/ published_at / collected_at / extract_status。

**异常隔离**:单源失败不影响其他源(各自 try/except,吞异常记日志继续)。

## ⚙️ 5. 事件处理层

**入口**:`processors/event_processor.py` 的 `process_all(db) → ExtractResult`

**三个子模块**:
- `event_extractor.py`:单条 `RawNews` → LLM 结构化抽取 → `ExtractedEvent`。Prompt 模板外置 `config/prompts/event_extraction.txt`,`lru_cache` 读一次。
- `event_dedup.py`:基于**标题字符 bigram 覆盖度**的去重合并判定(非 Jaccard)。
- `event_processor.py`:编排——读未处理新闻、调抽取、合并判定、写库。

**「已处理」状态机**(`raw_news.extract_status` 字段):

| 取值 | 含义 | 是否再取 |
|---|---|---|
| `pending` | 待处理(新采集) | ✅ 被 `_load_unprocessed_news` 取出 |
| `extracted` | 成功抽取并写入 event_sources | ❌ 永久跳过 |
| `noise` | LLM 判为非事件(`event_type == "other"`) | ❌ 永久跳过 |
| `failed` | LLM 返回 None / 异常 / 429 限流 | ❌ 永久跳过 |

> 运维兜底:重处理单条可手动 `UPDATE raw_news SET extract_status='pending' WHERE id=<X>`。

**去重合并算法**:`find_mergeable(title, event_type, candidates, threshold=0.6)`
- 合并键 = `event_type` 相同 + 标题字符 bigram **覆盖度** `max(|A∩B|/|A|, |A∩B|/|B|)` ≥ 0.6。
- 刻意用覆盖度而非 Jaccard:真实新闻标题常一长一短(同一事件不同详略),Jaccard 分母被长串拉大;覆盖度衡量「短串核心 bigram 是否都在长串里」,对长度差更鲁棒。
- 合并候选池 = DB 近 7 天既有 events + 本批次已生成 events(`_MERGE_LOOKBACK_DAYS`),使同批次内重复新闻互相合并。
- `event_subject` 抽取但不作合并键(LLM 对主体命名不稳定)。

**产物表 `events`**:event_id(展示码 `EVT_YYYYMMDD_NNN`,当日序号定宽 3 位)/ event_title / event_type / event_subject / event_time / summary / source_count / status / created_at。真正主键是整型 `id`,所有外键指向 `id`。

**关联表 `event_sources`**:`(event_id, raw_news_id)` 组合唯一,`source_count` = 关联行数。

## 🧠 6. 推理分析层

**入口**:`analysis/analysis_processor.py` 的 `analyze_all(db) → AnalyzeResult`

**两个子模块**:
- `event_analyzer.py`:单个 `Event` → LLM 投资影响分析 → `AnalyzedEvent`。Prompt 模板 `config/prompts/event_analysis.txt`。
- `analysis_processor.py`:并发编排。

**未分析判定**:**不加状态字段、不加迁移**。未分析 = `events.id NOT IN (SELECT event_id FROM event_analysis)`(NOT IN 子查询)。与处理层不同——分析层每个事件都应被分析、失败可重试,故保持反查模式。

**并发**:`ThreadPoolExecutor` 并行调 LLM,`_MAX_WORKERS = 200`(小米 MiMo 无限流可调高;DeepSeek 限流时建议降到 1-3)。结果先全部收集再统一 `db.commit()`。

**限流重试**:`event_analyzer` 检测 429/rate limit 错误,指数退避(2s → 4s → 8s),最多 `_MAX_RETRIES = 3` 次;其他异常直接返回 `None`(隔离不中断整批)。

**结构化输出**:schema `AnalyzedEvent`(`importance_score` 1-5、`importance_level` S/A/B/C、`affected_industries` / `affected_assets` / `causal_chain` / `positive_factors` / `negative_factors` / `risk_warning`)。Prompt 约束两者自洽。结构化模型在模块级惰性构造一次复用,切换 provider 后调 `reset_model_cache()`。

**产物表 `event_analysis`**:与 `events` 一对一(FK 上加 UNIQUE 约束强制)。JSON 数组字段用可移植 `JSON` 类型(SQLite 存 TEXT、PG 存 json)。`model_version` 记 `provider/model` 便于追溯。

## 🛠️ 7. LLM 服务层

**位置**:`app/services/llm/`(`factory.py` + `providers.py`)

**统一入口**:
- `create_model(model_name?, provider?, **kwargs) → BaseChatModel`
- `create_structured_model(schema, ...) → Runnable`(底层 `with_structured_output(schema)`,`invoke` 直接返回 schema 实例,**不要自己解析 JSON**)

**四方支持**(注册在 `_BUILDERS` 字典):

| provider | 底层类 | 读环境变量 | 备注 |
|---|---|---|---|
| `deepseek` | `ChatDeepSeek` | `DEEPSEEK_API_KEY`(SDK 自动) | |
| `qwen` | `ChatTongyi` | `DASHSCOPE_API_KEY`(SDK 自动) | 通义千问 |
| `openai` | `ChatOpenAI` | `OPENAI_API_KEY`(SDK 自动) | |
| `xiaomi` | `ChatOpenAI` | `XIAOMI_API_KEY`(**显式读取**) | OpenAI 兼容,`base_url=https://api.xiaomimimo.com/v1` |

**原则**:所有 LLM 调用走工厂,不在业务代码直接实例化;provider/model 缺省取 `config/llm.yaml`(当前默认 `xiaomi` / `mimo-v2.5-pro`);`.env` 在配置加载时由 `_ensure_dotenv()` 注入。

## 🖥️ 8. 产品服务层(API)

**入口**:`app/main.py`,所有路由挂 `/api` 前缀,CORS 允许 `localhost:3000`,`lifespan` 启动时建表 + 启停定时任务。

| 方法 | 路径 | 说明 | 鉴权 |
|---|---|---|---|
| GET | `/health` | 健康检查 `{status: ok}` | 开放 |
| GET | `/api/events` | 事件列表,支持 `event_type`/`importance_level`/`start_time`/`end_time` 筛选 + `limit`/`offset` 分页,按 `created_at` 倒序,LEFT JOIN 填充等级 | 开放 |
| GET | `/api/events/{id}` | 事件详情:主信息 + sources + analysis(`selectinload` 防 N+1,无则 404) | 开放 |
| GET | `/api/events/{id}/card` | 事件卡片(扁平视图,无分析时降级 None/空数组) | 开放 |
| GET | `/api/stats` | Dashboard 聚合:totals + 类型分布 + 等级分布 + 14 天趋势 + 来源分布 + S·A 级重要事件流 | 开放 |
| POST | `/api/jobs/collect` | 手动触发 RSS 采集 | 开放 |
| POST | `/api/jobs/extract` | 手动触发事件抽取 | 开放 |
| POST | `/api/jobs/analyze` | 手动触发事件分析(并发) | 开放 |

| GET | `/api/auth/me` | 返回当前登录用户(从 cookie 读 JWT) | **需登录** |

> 鉴权范围:仅 `/api/auth/me` 需登录。事件/统计/采集 API 保持开放,符合「仅新增登录能力」的 MVP 决策。

## 🔐 9. 用户鉴权

**范围**:仅新增注册/登录能力。现有事件/统计/采集接口保持开放,登录后在导航栏显示用户名 + 登出按钮。

**机制**:bcrypt 密码哈希 + JWT(HS256)+ httpOnly Cookie。

| 决策项 | 选型 |
|---|---|
| 登录标识 | 用户名(username)唯一,3-64 字符,不含空白;邮箱可选 |
| 密码哈希 | bcrypt(rounds=12);超 72 字节密码先 SHA-256 派生再 bcrypt |
| Token | JWT HS256,`sub=username`,过期 24 小时(`config/security.yaml`) |
| 存储 | httpOnly Cookie(`ea_auth_token`),HttpOnly 防 XSS,SameSite=Lax |
| 防枚举 | 登录失败(密码错 / 用户不存在)统一返回 401「用户名或密码错误」 |

**模块**:
- `app/core/security.py`(纯函数):`hash_password` / `verify_password` / `create_access_token` / `decode_access_token`。`SECRET_KEY` 走 `.env`,其余参数走 `security.yaml`。
- `app/api/deps.py`:`get_current_user(request, db)` 从 cookie 读 token,解码后查 User 表,无效则 401。
- `app/api/v1/auth.py`:register(201,成功即 Set-Cookie 自动登录)/ login / logout(204)/ me。
- `app/models/user.py`:users 表。

## ⏱️ 10. 定时任务

**文件**:`app/scheduler.py`,在 `main.py` lifespan 中起后台 daemon 线程。

- 间隔:`INTERVAL_SECONDS = 1800`(30 分钟);首次延迟 `_INITIAL_DELAY = 10` 秒。
- 流程:`_run_pipeline` 串行执行 `collect_all → process_all → analyze_all`,单步失败不阻塞后续(各自 try/except)。
- 启停:`start_scheduler()` 返回 `threading.Event`,`stop_scheduler()` 通过 `Event.set()` 优雅退出。

**技术**:Next.js 15 App Router + React 19 + TypeScript + Tailwind v4,强制暗色金融终端风格。

### 页面路由

| 路由 | 类型 | 职责 |
|---|---|---|
| `/` | Server Component | Dashboard 控制台:KPI 四卡 + 类型/等级/趋势三图表 + 重要事件流 |
| `/events` | Server Component | 事件库列表:筛选(类型/等级/日期)+ 分页 |

### 数据流

```
Server Component ──直连──→ BACKEND_URL/api   (Node fetch 需绝对地址)
Client Component ──同源──→ /api ──[rewrites]──→ BACKEND_URL/api   (浏览器自动带 cookie)
```

- `lib/api.ts`:`API_BASE` 双模式(Server 用 `BACKEND_URL`,Client 走 `/api` 由 `next.config.mjs` rewrites 代理)。`getJson`/`postJson` 统一带 `credentials: "include"`。
- `fetchMeServer()`:Server Component 从 `next/headers` 的 `cookies()` 读 `ea_auth_token`,手动设 Cookie 头转发后端。

## 🗄️ 12. 数据库

SQLite 同步引擎,5 张表:

| 表 | 职责 | 关键约束 |
|---|---|---|
| `raw_news` | 原始新闻 | `content_hash` UNIQUE(主去重键);`extract_status` 状态字段 |
| `events` | 结构化事件 | `event_id` UNIQUE(展示码);整型 `id` 是真正主键 |
| `event_sources` | 事件↔新闻多源关联 | `(event_id, raw_news_id)` 组合唯一 |
| `event_analysis` | 投资影响分析 | 与 events 一对一(FK 上 UNIQUE);`importance_score` CHECK 1-5 |
| `users` | 用户 | `username` UNIQUE;`password_hash` bcrypt;`email` 可选 UNIQUE |

**基础设施约定**:
- 同步引擎(MVP 批处理,无高并发 HTTP 需求;Alembic autogenerate 在同步引擎下最简单)。
- SQLite 默认不强制外键,connect 事件开 `PRAGMA foreign_keys=ON` 使 `ondelete=CASCADE` 生效。
- 时间统一 UTC naive datetime(`utcnow()` 作为 Python default;不用 `func.now()` 避免写本地时间)。
- Alembic `env.py` 用 `render_as_batch=True`(SQLite ALTER 受限,批模式重建表)+ `compare_type=True`(检测列类型变更)。
- `main.py` lifespan 用 `Base.metadata.create_all` 兜底建表,正式 schema 变更走 Alembic。

## 📌 18. 关键设计取舍

| 取舍 | 原因 |
|---|---|
| 同步 SQLAlchemy 而非异步 | MVP 批处理流水线为主,无高并发 HTTP;Alembic autogenerate 在同步下最简单 |
| SQLite 而非 PG | 单文件零运维,MVP 够用;JSON 类型用可移植写法,可平滑迁 PG |
| `extract_status` 状态字段(处理层) | 早期用 `NOT IN event_sources` 反查会让噪声/失败新闻每轮被重取、反复调 LLM;状态字段一次性标记后跳过 |
| 分析层不加状态字段 | 每个事件都应被分析、失败可重试,反查 `NOT IN event_analysis` 足够,无需迁移 |
| bigram 覆盖度而非 Jaccard | 真实新闻标题常一长一短,Jaccard 对长度差敏感;覆盖度衡量短串核心 bigram 是否都在长串里 |
| httpOnly Cookie 而非 localStorage | XSS 安全 + Server Component 可通过 `cookies()` 读取,SSR 友好 |
| bcrypt 原生包而非 passlib | passlib 1.7.4 与 bcrypt 5 不兼容(废弃 API);bcrypt 4.x 原生 API 稳定,依赖更少 |
| 无前端 Provider/Context | 鉴权用 `auth-change` 自定义事件 + `fetchMe`,零新依赖,登录态变化频率低 |
| LLM 统一工厂 | 不在业务代码直接实例化;结构化输出由 SDK 完成;Prompt 与代码分离 |
